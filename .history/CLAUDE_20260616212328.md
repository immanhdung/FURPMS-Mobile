# FURPMS Mobile Application Guidelines

## Project

FPT University Research Project Management System (FURPMS)

Mobile Application

Frontend Only

Built with:

- React Native
- Expo
- Expo Router
- NativeWind
- React Query
- React Hook Form
- Zod
- React Native Reanimated
- React Native Gesture Handler
- Expo Secure Store

---

# Project Goal

This mobile application is an extension of the FURPMS Web System.

The mobile app is primarily designed for:

1. Faculty
2. Review Committee

Admin and Staff remain web-first experiences.

---

# Architecture Philosophy

This is a Software Engineering Graduation Capstone Project.

The architecture must prioritize:

1. Maintainability
2. Scalability
3. Reusability
4. Readability
5. Future API Integration

---

# API-Ready Architecture

API contracts already exist.

Backend implementation is not completed.

Build the application using API-ready architecture.

All screens must consume services.

All services currently return mock data.

Future API integration should only require changes inside services.

UI must never call APIs directly.

Never place business logic inside screens.

---

# Folder Structure

Use Feature-Based Architecture.

src/

├── app
├── features
├── shared
├── services
├── hooks
├── providers
├── constants
├── utils
├── assets

---

# Feature Structure

feature/

├── screens
├── components
├── hooks
├── services
├── types

Features:

- auth
- faculty
- reviewCommittee
- notification
- search
- meeting
- profile

---

# State Management

Use:

- React Query for server state
- Context for global app state
- Local state for UI state

Avoid unnecessary global state.

---

# Navigation

Use Expo Router.

Structure:

- Auth Stack
- Main Tabs
- Nested Stacks

Navigation must remain scalable.

---

# Services

Create service modules.

Examples:

- auth.service
- proposal.service
- review.service
- meeting.service
- notification.service

Services should return mock data.

Screens must never import mock data directly.

---

# Component Rules

Create reusable components.

Shared:

- Button
- Card
- Input
- SearchBar
- Avatar
- Badge
- EmptyState
- ErrorState
- LoadingState
- Timeline
- Modal
- BottomSheet

Avoid duplicate UI.

# Coding Standards

- Functional Components Only
- Hooks Only
- Clean Code
- Consistent Naming
- Small Components
- Reusable Architecture

Avoid:

- Massive files
- Direct API calls
- Duplicated code

# Future Integration

When backend is completed:

Only service implementations should change.

Screens, hooks, components, navigation, and layouts should remain unchanged.
